# Patch the pinned Nitro nightly for production

The Portal build depends on `nitro-nightly@4.0.0-20251010-091516-7cafddba` (aliased as `nitro`, per ADR-0013 and ADR-0015). Every production build of that version silently drops the shim that lets its own catch-all SSR route serve itself in-process: Nitro's `virtual()` rollup plugin returns an unmarked module id for the `#nitro-internal-pollyfills` virtual, so rolldown tree-shakes it away as dead code, and with it the `setupVite()` call it exists to trigger. Without that shim, every document request makes a real outbound HTTP call to the server's own public origin and recurses on itself with no bound, exhausting the host. The system carries a one-line patch to that file, applied with `pnpm patch` and committed at `patches/nitro-nightly@4.0.0-20251010-091516-7cafddba.patch`, rather than working around the defect at the application or proxy layer.

Two alternatives were tested and rejected. The newest available `4.x` nightly (`20251030-211409`) reproduces the identical defect — its production `fetch` override still has no branch for Nitro's internal `viteEnv`-tagged service dispatch — so bumping buys nothing, while also requiring `vite.config.ts`'s handler paths to be rewritten for an unrelated resolution change in that nightly. The stable `nitro@3` line is not a version bump but an API break: `defineNitroPlugin` was renamed to `definePlugin` and relocated off the `nitro/runtime` subpath the codebase imports it from, and the package's own bundled migration guide confirms this is one of several such moves. Working around the defect without patching — routing `/**` ourselves in `vite.config.ts`, or re-adding the Caddy-layer symptoms this originally produced (see the reverted header-stripping and `NODE_OPTIONS`/`--max-http-header-size` churn in git history) — was rejected because it treats a build defect as an infrastructure problem, leaving the real defect free to resurface silently.

This narrows ADR-0015's commitment to "exact TanStack versions" further than that ADR anticipated: the system now also carries a hand patch against Nitro's internals, not just a version pin. `apps/portal/scripts/check-ssr-shim.mjs` runs as a build step specifically to catch the patch silently ceasing to apply. Both `apps/portal/Dockerfile` and `apps/auth/Dockerfile` must `COPY patches` before `pnpm install`, since `patches/` holds the file `pnpm.patchedDependencies` in `pnpm-workspace.yaml` points at. Any future Nitro upgrade must independently re-verify this defect against the target version — a passing build is not sufficient evidence, as shown above — and account for the handler-path resolution change observed between nightlies.
